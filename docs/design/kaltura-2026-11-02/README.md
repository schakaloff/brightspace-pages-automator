# Kaltura workflow audit and previews

Investigation date: 2 November 2026. This document records the original audit and approved proposals; descriptions of the old behavior below are historical. The approved changes are now implemented in the working tree. See [implementation and validation](IMPLEMENTATION.md) for the current state and remaining live checks.

The main problem is trust and recovery, as well as appearance. The workflow opens several browsers, exposes most state through a log, and loses the distinction between a successful write, a failed write and a write whose outcome is unknown. A visual refresh should sit on top of explicit, saved operation states rather than a percentage inferred from log text.

## What happens today, from beginning to end

| Step | Automation | What Nick must decide or do | Progress, failures and retries today |
|---|---|---|---|
| 1. Enter courses | Loads the two last-used URLs from app configuration. | Paste Moodle and Brightspace course URLs; credentials can be stored through Settings. | Only these URLs are saved by the Kaltura panel. No scan, selections, destinations or page outcomes are saved. |
| 2. Start discovery | “Find Videos & Suggest Destinations” checks whether the Moodle session file exists. If absent, opens a visible Moodle login browser. | Sign in manually if credentials are absent. | Saved credentials use Moodle's manual login page. Manual login waits up to six minutes. A file's existence is not proof that a session is valid. |
| 3. Validate Moodle | A separate **headless** browser opens the whole course using saved cookies. Removes section-specific query parameters; rejects activity/section-ID URLs. | Usually no action. A stale session can open a visible login browser again. | Up to four enrolment redirects are retried. A saved session that appears stale is refreshed once and the scan is restarted once. Invalid course coverage fails explicitly. |
| 4. Scan videos | Loads the complete activity listing, enabling Edit mode if necessary. Reads course-page embeds, Kaltura resources, assignment descriptions, pages, books and chapters. Resolves some player titles. | Wait; source scans are not currently visible in a browser. | Logs activity/chapter visits. Individual activity/chapter errors are skipped and scanning continues. This partial coverage is not returned as structured data. YouTube discoveries are logged separately, not sent to KMC. Learner submissions are excluded. |
| 5. Deduplicate scan | Keeps one result per Kaltura entry ID for the entire course. | Cannot review additional occurrences of that video. | Prevents repeated scan results, but retains only the first occurrence's title and section. This is **not** destination duplicate prevention. |
| 6. Read Brightspace | Opens another visible browser using the shared launcher and login helper. Reads the table-of-contents API, flattening modules into ID/title choices. | Complete Brightspace sign-in/MFA if prompted. | The shared helper waits up to nine minutes. API errors currently become an empty module list, making failure look like a course with no units. |
| 7. Suggest destinations | Reuses `content_matcher.match_sections`. Suggestions at 75+ are assigned; groups at 90+ are selected automatically. | Open/review the separate results window; change destinations and select individual videos or groups. | Lower-confidence/unmapped groups are unchecked. There is no final binding between this plan and the course URLs, which become editable again. |
| 8. Prepare new units | A destination can be an existing unit or a named pending new unit. Typing a matching existing name reuses it. | Name any new units. | Pending names are collected from **all mapped groups**, including groups with no selected videos. Only “at least one destination exists” is validated. |
| 9. Approve writes | Shows a warning with selected-video and mapped-module counts and any new unit names. | Approve or cancel live Brightspace changes. | Cancellation here creates no pages. This is the one current explicit write-approval gate; it does not provide a per-video validated plan. |
| 10. Create units | Opens another Brightspace browser. Reuses matching unit names, creates missing units through `bs_units.create_unit`, rereads the TOC to resolve IDs. | Wait or complete login again. | Failed units are dropped from the map and their videos are skipped. KMC has not been connected yet: units can be created before a later KMC login fails. No per-unit journal survives a restart. |
| 11. Connect KMC | Opens a visible Kaltura Management Console browser using its own saved session. Tries KMC native credentials, then Microsoft SSO; falls back to manual login. | Complete sign-in/MFA if needed, after already approving creation. | Credential-based SSO polls for roughly three minutes. Manual fallback waits indefinitely until the entries list appears or the browser is closed. The wait is not represented as an attention state in the app. |
| 12. Connect destination writer | Opens a second visible browser for Brightspace page creation and verifies/recoveries its session. | Complete another login if required. | Uses a separate browser-launch path from the shared launcher; sessions are shared but live contexts are not. Failed recovery can return without a structured failure result. |
| 13. Create each page | For each selected, mapped entry: search KMC, open the first result, capture Share & Embed HTML, navigate to the destination, create Page, paste into Source Code, set title, Save and Close. | Mostly watch browser windows or read the log. | Missing map/embed code or an item exception causes a skip/continue. Save-button click plus a wait is counted as success; no saved topic ID, embed ID, destination or final title is read back. |
| 14. End | Saves KMC browser cookies, closes browsers, posts `__CAT_DONE__`. | Infer the outcome from the log. Can click Create again with the same selections. | Success, partial failure, total failure and early return share the same completion event. Selections remain. There is no structured result screen, safe Stop, Back flow, transfer library or retry-only-failed command. |

## Findings, in implementation order

P1 means fix before shipping the redesigned workflow. P2 means a material usability, reliability or maintenance gap. No production-data loss was demonstrated; live courses were not used.

| Priority | Finding and evidence | User impact | Recommended change |
|---|---|---|---|
| P1 | **No destination reconciliation or persistent write journal.** `embed_entries` creates every selected video again. `_create_bs_page` returns `True` after Save without reading the result (categorizer lines 1314–1332, 1337–1440). | A repeat run can create duplicates; a timeout after a successful save cannot be safely interpreted. | Persist write intent before Save, capture any topic ID immediately, then independently verify destination membership, title and embedded entry ID. Reconcile uncertain work before allowing creation again. |
| P1 | **Old plan can be applied to a changed course URL.** `_apply_state(RESULTS)` reenables URL fields; `_start_create_pages` combines their current text with old selections/module IDs (panel lines 685, 933). Reproduced in `audit-probes.json`. | The backend receives stale destination IDs for another target; the approved plan is no longer reliably tied to the scanned course pair. | Bind plan to normalized source/target identities. “Change courses” starts a new plan; validate IDs against a fresh, complete destination read before approval/application. |
| P1 | **Unselected groups can create units.** `pending_module_names()` traverses the entire section map (panel lines 333–354, 947–999). Reproduced with an unselected “Empty unit” group. | Side effects exceed the selected video plan; displayed destination counts include unrelated groups. | Derive destinations and new units only from selected rows. Persist each resolved new unit ID. |
| P1 | **Incomplete mappings pass validation.** The panel only tests whether `section_map` is nonempty; unmapped selected entries reach the backend and are skipped (panel lines 943, categorizer line 1421). Reproduced with two selected videos and one usable mapping. | “Create 2 pages” can silently attempt just one. | Block approval until every selected occurrence has a valid destination; make excluded rows explicit. |
| P1 | **Login failure announces success.** Both login paths send `__LOGIN_DONE__`, and the poller always logs “Moodle session saved” (panel lines 779, 785, 1044). Reproduced with a synthetic login exception. | The user is told they are connected when the action failed. | Typed success/failure/cancelled events with verified connection evidence; retain the sign-in prompt on failure. |
| P1 | **Completion hides partial and total failure.** `embed_entries` returns `None`; errors, early returns and normal termination all reach the same `__CAT_DONE__` handler (panel lines 1013–1034, 1080). | The primary action returns ready to repeat the whole selection. The user has no trustworthy result or recovery action. | Return and persist item outcomes, scan coverage and run outcome. Count only independently verified pages as created; preserve “Needs checking.” |
| P1 | **Read errors masquerade as empty data.** Module fetch/creation helpers log TOC errors and return `[]` (categorizer lines 719–724, 807–811). Activity/chapter exceptions are skipped without a coverage result (543–548). | A failed inventory can look like “no videos” or “no units.” Unit creation may proceed without reliable knowledge of existing units. | Return complete/partial/failed read states and unread URLs. Require complete destination inventory for duplicate prevention; let users retry failed source reads. |
| P1 | **KMC result identity and editor content are not verified.** `_get_embed_code` clicks `rows.first` after searching, without checking the row/HTML entry ID (869). Missing title input logs a warning and still saves (1314); failed editor focus is not checked before Ctrl+A/paste. | A page can be incorrectly titled or contain the wrong/missing embed while appearing saved. | Require an exact KMC entry match and validate captured embed ID. Fail before save if editor content/title cannot be confirmed. Read the saved page back after save. |
| P2 | **Overlapping workers and mutable review.** Advanced actions disable only their own button and share one queue; all worker callbacks lack a run ID. The results dialog does not freeze selection/destination widgets while creation runs (panel lines 442, 760, 866, 898). | Out-of-order results can replace the current plan; edits during a run can disagree with the worker's captured copy. | One active operation per panel, tagged events, immutable approved snapshot and disabled editable review during writes. Lock the destination course against concurrent writers, not just a single run file. |
| P2 | **Global deduplication loses placement decisions.** One `seen_entries` set covers every source section (categorizer lines 388, 440). Group maps use section **names**, so distinct sections with the same title merge. | Legitimate repeated video placements and repeated section names lose context. | Keep one media identity plus every source occurrence, with stable source section/activity IDs. Let the user approve one or more placements. Default duplicate key: destination course + module ID + entry ID. |
| P2 | **Login and scan attention are hidden.** Login is buried in Advanced tools, KMC sign-in starts after write approval, discovery is headless, status lives in logs, and ETA copy disagrees (“2–5” versus “5–10” minutes). | Users cannot tell whether to wait, sign in, review, or intervene. | Persistent attention region with service, actual wait reason and next action; connect all services before write approval, reauthenticate explicitly if later required. Use measured item counts and elapsed time, not a fabricated ETA. |
| P2 | **Visual/theming and accessibility drift.** Kaltura bypasses `design='modern'`, uses inline dark warning colors and custom teal/manual-button styles, has an empty `apply_theme`, icon-only expand buttons without explicit accessible names, and no outer scroll container (panel lines 141, 471–649, 1127). | Inconsistent Media/H5P appearance; weaker light-theme legibility and short-window behavior; expand actions are difficult to identify with assistive tools. | Use shared theme roles/icons, form buddies and names, visible focus and text status. Scroll body content while keeping primary actions visible. Verify Windows accessibility and scaling during implementation. |

Some findings follow directly from source and were not exercised against a live LMS. The four UI orchestration probes intentionally stub all backend calls. Their output also confirms that the old “Create Pages for 2 Selected Videos” action remains available after the synthetic run.

### What already works and should be preserved

- Whole-course URL normalization, stale Moodle session retry and incomplete-course guards already prevent several false-empty scans.
- Book chapter coverage, nested-section ownership, course-page embeds, provider-specific YouTube detection and assignment-description scoping have useful existing fixture coverage.
- Shared section matching, `bs_units.create_unit`, existing-name reuse, TOC ID rereads and responsive Brightspace Create New/Add menu fallbacks are valuable. Preserve these while adding verification boundaries.
- Scan and write browser work happens off the Qt UI thread. Preserve that responsiveness.
- The live-write warning already establishes an explicit approval moment. Make its content a precise, saved plan.

## Proposed flow: Connect → Review → Create → Results

| Phase | Main screen and action | Attention and truth rules |
|---|---|---|
| **Connect** | Enter courses, choose cursor visibility, “Connect & find videos.” Show separate Moodle, Brightspace and KMC states, then read source videos and destination inventory. | “Sign in to Kaltura,” “Complete Brightspace MFA,” and “Scanning book chapters” are different states. Login continues only on a verified service-specific signal. Allow Cancel/Stop. During discovery, show candidate visits/chapters and actual coverage; the total can grow as books are opened. |
| **Review** | Show immutable course identity, searchable grouped videos, all source occurrences, proposed unit for each placement, existing pages, exclusions and any incomplete scan. “Approve & create N pages.” | Never preselect unmapped items. Show new units separately. Explain duplicate grouping and let the user choose repeated placements. The approval summary includes the exact target course ID and all side effects. If scan coverage is partial, show the gaps and offer retry; require explicit acknowledgement for applying a partial source plan. A complete destination check remains mandatory. |
| **Create** | Show current service, video, destination and action; reuse existing automation cursor and messages. “Stop.” | Count only verified outcomes, e.g. “2 verified · 1 being checked · 3 not started.” Source scan counts and page counts have separate denominators. A successful button click does not mean a saved page. |
| **Results** | Show created/verified, already present/kept, excluded, not started, failed-before-save and needs-checking groups. Link to verified pages and destinations. | “Check & continue” reconciles uncertain saves first. “Retry failed reads” is distinct from “Create remaining pages.” Never promise automatic rollback. Complete means all approved placements have been verified or explicitly accounted for by an approved exclusion. |

Connect can contain read-only substages; it does not need extra top-level phase tiles. KMC connection is a preflight, and may be requested again later if the session expires. Browser automation stays best-effort visually: an overlay failure must never cause a backend operation to fail.

## Back, Stop and recovery contract

| Situation | Save now / future journal | Safe recovery behavior |
|---|---|---|
| Before discovery | Sanitized course identities, chosen options and timestamps. Never credentials/cookies in transfer JSON. | Close/back creates no course pages. Browser sessions remain separate from transfer records. |
| During source discovery | Successful visits, unread/failed URLs, source occurrences and coverage completeness. | Stop at a bounded read boundary. Resume/retry failed reads; do not call a partial scan “no videos.” Reread freshness-sensitive inventory before approval. |
| During review | Selections, destination IDs/new-unit intent, exclusions and the exact course pair. | Back keeps this draft. Changing the course pair creates a new plan. Changing selections invalidates the prior approval. |
| New unit creation | Record pending intent **before** mutation, then returned/resolved unit ID and verification. | Recheck destination and reuse the verified unit on resume. A failed TOC read blocks creation; it never establishes that the unit is missing. Ambiguous equal titles require a user choice. |
| Before page save | Stable placement key, entry ID, intended title, target unit, state and attempt history. | Retry a confirmed pre-save failure after revalidating the destination. Reuse cached embed HTML only after checking its media identity/freshness. No video download/upload is involved in this Kaltura flow. |
| During/after Save | Persist pending state before click, capture topic ID as soon as available, then verify content and destination. | Stop requests a pause. Finish a bounded verification of the current write, or leave it uncertain. Do not force-kill an in-flight write as the normal Stop behavior. |
| Restart after crash | Journal survives, browser sessions may have expired. | Reconnect, lock target, reread modules/topics and inspect saved content. Verify a known topic ID or reconcile by unit + exact entry ID. Titles alone are insufficient. Multiple matches or unreadable content require attention. |
| Retry uncertain page | Keep uncertain status and all known IDs. | Do not automatically repeat Save/create. If a trustworthy complete check proves absence, return it to a reviewable “ready” state and request approval for creation. If existence cannot be established, remain blocked for that placement and allow safe unrelated work. |
| Remove saved transfer | Set a reversible removal marker; keep journal and original work timestamps. | Hide from the default list; provide Undo and a Removed filter with Restore. Do not delete Kaltura media, Moodle content, Brightspace pages or recovery evidence. A new transfer must still reconcile destination content, including work recorded in removed history. |

The current implementation cannot safely offer these resume semantics by adding a button alone. It needs persistent Kaltura outcomes and reconciliation first. Pre-existing pages that have no transfer journal should be inspected conservatively; no speculative “previously created” status.

## Saved library behavior

Use H5P's Course / Progress / Last saved table. Search course names, source and target IDs, media/transfer IDs where applicable; show a short transfer ID in the row and the full ID in a tooltip/details/copy action. Filters: All saved, Needs attention, Ready to review, Complete, No Kaltura videos, Removed. Include created and updated dates in transfer details, with work timestamps unchanged by removal/restoration.

“Needs attention” includes partial scans, missing destinations, verified pre-save failures, changed destinations and uncertain writes. “No Kaltura videos” is permitted only after complete source coverage. An interrupted run is normalized to a recoverable state on open; it must not look actively running after a crash. Removal during an active run is refused using the same lock as the runner; bulk removal can explain which entries remain busy.

## Validation and limits

- **40 existing tests passed**: all `test_kaltura_scan.py`, `test_h5p_saved_transfers.py`, `test_h5p_browser_guide.py` and `test_h5p_progress.py`. This covers intercepted source scans, library removal/search/locking, progress persistence/reconciliation and guide behavior. It does not establish that Kaltura currently implements H5P's recovery.
- **7 additional browser-guide tests passed**, covering actual cursor visibility, real clicks, password exclusion, cross-origin/frame coordinates, navigation/new tabs and motion behavior. Total: **47 selected existing tests passed**.
- `probe_current_workflow.py` reproduces four Kaltura orchestration issues entirely in memory: false login success, unselected-unit creation, incomplete selected mapping, and applying old mappings to a changed course URL. [Probe output](C:/dev/brightspace-automator/brightspace-pages-automator/docs/design/kaltura-2026-11-02/audit-probes.json).
- The async fixture checks required execution outside the sandbox: the restricted Windows environment hung in `socket.socketpair()` while starting even an empty asyncio event loop. No app change was made to work around that environment restriction. Fixture requests were intercepted; no live course was contacted.
- Qt previews were rendered in light/dark at standard and small sizes and visually inspected. The library adapts the actual H5P view with an in-memory provider and larger rows to avoid clipped status text. Search/selection/removal/Undo/restore use local sample state; other proposal buttons are visual, not live automation.
- The web-only Impeccable detector is not a Qt accessibility or performance checker. No browser-DOM score or WCAG compliance claim is made. Keyboard/screen-reader announcements, high-DPI/text scaling, packaged launch behavior, real MFA and live save verification remain implementation/release checks.
